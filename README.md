# 单词君 · 微信小程序版

「单词君」的微信小程序版本（Taro + React + TypeScript）。

## 功能

页面分四层，每层一个独立路由（2026-10 在主界面前面又加了一层封面）：

```
主界面（封面）──「背单词」──┬── 大学六级（官方词书）──┐
                            │                        │
                            └── 我的上传 ── 某本书 ──┤
                                                     ↓
                                    高频词 / 中频词 / 低频词 / 完整词表
                                                     ↓
                                                  翻书
```

| 路由 | 页面 |
| --- | --- |
| `pages/home/index` | **主界面（启动页）**：封面 + 「背单词」，只放要动手的事 |
| `pages/stats/index` | **数据**（主界面子页）：节奏 / 累计 / 词汇 / 生词库，统计都在这儿 |
| `pages/plan/index` | 计划（主界面子页）：定「某天前背完某本书」+ 实时领先/落后 |
| `pages/index/index` | 第二层 · 词书列表（点「背单词」进来） |
| `pages/uploads/index` | 第二层 ·「我的上传」书目列表 |
| `pages/levels/index` | 第三层 · 档次（`?bookId=` 指定词书） |
| `pages/reader/index` | 第四层 · 翻书（`?bookId=&level=`） |
| `pages/vocab/index` | 生词本（底部 Tab 栏的第二个 Tab）—— **只放复习设置和入口，不显示单词** |
| `pages/mastered/index` | 熟练掌握词汇（底部 Tab 栏的第三个 Tab） |
| `pages/review/index` | 复习（子页，一屏一词的卡片式复习，`?size=` 这一批几个） |
| `pages/review-log/index` | 复习记录（子页，按标记 7~1 分档的目录） |
| `pages/review-level/index` | 标记档位（子页，`?level=1..7`：这一档的全部单词 + 随机抽查） |
| `pages/vocab-all/index` | 全部生词（子页，一次性列出整个生词库） |

> ⚠️ **`app.config.ts` 的 `pages` 数组第一项就是启动页** —— 现在是 `pages/home/index`。
> 想换启动页就动那一行的顺序，别去别处找「首页」配置。

**没有原生 tabBar，但翻书页、生词本、熟练掌握词汇底部有自绘的 Tab 栏**（`components/tab-bar.tsx`，三个 Tab：翻书 / 生词本 / 熟练掌握词汇）。
不用微信原生 tabBar 的原因：它是 `app.config.ts` 里编译期写死的，而翻书页必须带 `?bookId=&level=` 才知道翻哪本书，
原生 Tab 给不了参数；`switchTab` 还会把页面栈清空，翻书页左上角的「返回」就废了。
所以自绘一个普通 View 放在页面最后一行——顺便解决了原来的坑：生词本入口放右上角会被微信原生胶囊（… 和 ○）盖住。

> **「我的」页 2026-10 按用户要求整页删掉**：`src/pages/mine/`、`app.config.ts` 里的注册、
> 底部 Tab 栏和首页那两处入口一起没的（第三个 Tab 换成了「熟练掌握词汇」）。
> 云同步**不受影响**——它在 `app.ts` 里静默跑，登录不依赖任何页面。

> 「熟练掌握词汇」和生词本一样是**从底部 Tab 栏进的**，词书列表上没有入口——那一页没有这个 Tab 栏。

**主界面 · 封面**（`pages/home`，启动页。用户 2026-10 提了五轮，演进过程值得留着别再走回头路）：

**封面为什么这么瘦**：统计（整体进度、节奏、预测、累计）已经单独成页，
封面留三件**要动手的事** —— 今天背多少（今日）、计划还差多少（计划）、接着翻哪个词（词卡），
外加一个主操作。**别的都别往这里加**，一加就回到二版那种「乱」。

**四条排版纪律（封面和数据页共用）**：

1. **一套栅格**：`今日` / `计划` 等行共用**一条固定的标签列（144rpx）**，值永远从同一个 x 开始；
   卡片只留一张（词卡）—— 卡片是「卡片堆」的来源。
2. **图形只做发丝级**：进度是 **4rpx** 细条、柱状图是细柱。图形越小越像「数据」，越大越像「仪表盘」。
3. **数字带层级**：主数字用主文字色，`/ 1824`、`个词` 这类单位退到次要色。
4. **一屏铺满、不滚动**（`100vh` flex + `space-between`）→ 留白由布局自动分配，内容不会跑到状态栏底下，
   所以在自定义导航栏的前提下**连导航栏都不需要**（也就不再有重复标题）。

⚠️ **「今日」那行的目标只有一个来源**（用户 2026-10 指出「今日和计划冲突了，两个都能改每天背多少」）：
| 有没有计划 | 今天该背多少 | 在哪儿改 | 点「今日」那行的行为 |
| --- | --- | --- | --- |
| 有计划 | **计划算出来的每天量**（`perDay`） | 计划页（改计划 / 一键放宽） | 进计划页 |
| 没有计划 | 独立的每日目标（`dailyGoal`） | 主界面「今日」那行 | 弹系统 ActionSheet（10/20/30/50） |

两者**不会同时生效**，所以不可能出现两个互相矛盾的数字；`dailyGoal` 也不会被删，
删掉计划之后它会重新生效。计划页上原来那颗「把每日目标设为 N 个词」的按钮已经删掉 ——
它正是让同一件事有两个入口的来源。

**数据页**（`pages/stats`，主界面第三个入口，用户要求「单独弄成一个界面专门分析数据」+「**不能乱**」）：

**「不能乱」在代码里就是六条硬纪律**（改这一页前先读一遍）：

1. **一套栅格**：所有行都是「标签列 144rpx + 值列」，值永远从同一个 x 开始；
   行内可点的那几行右侧才出现箭头，不可点的绝不出现。
2. **四个分区，每个只有一个职责**：节奏 / 累计 / 词汇 / 生词库。
3. **不要卡片、不要分割线**：分区之间只用 48rpx 空白 + 一行 22rpx 的灰色小标题。
   列表页那套玻璃卡片这里**一张都不用** —— 一页四张卡就是「卡片堆」，也是二版被骂「乱」的原因。
4. **两个字号、两种字色**：值 28rpx 主文字色；标签 / 单位 / 备注 22rpx 次要色。
5. **图形只有发丝级**：进度 4rpx 细条、图里是细柱；**全页只有一个彩色**（`COLOR.progress` 蓝 = 进度）。
6. **没有记录就不显示结论**，绝不编数字（没速度就不给预测行；一周没背就写「还没开始」而不是「达标 0 天」）。

**「节奏」那一块的用处**（用户先问「这个近七天的用处在哪里」，再说「优化成有用的」）：
它要回答的是**「我保持住了吗 / 照这样下去来不来得及」**，所以必须给出**判断标准**和**后果**。
原来只有 7 根柱子 —— 那是没有基线的数字，而且没数据时是 7 根死桩，看着像坏了。现在四件东西：

1. **一行灰色摘要**（「目标 30 个 · 每天约 12 个 · 达标 3 天」）：把图里那两种颜色说清楚，
   **图里不再塞任何标注**；
2. **目标底柱**（灰 `#C7C7CC`）+ **实际柱**（蓝，压在灰柱上）：做到目标 = 蓝柱顶齐灰柱顶，
   没做到 = 灰柱露出一截，超额 = 蓝柱冒出去。**全 0 时是 7 根满高灰柱**（图不空，也不再像一条分割线）；
3. **达标天数**：直接给结论，不用自己数柱子；
4. **结论行**（最关键的一句）：按实际速度预测**哪天背完**，并和计划的目标日期比 ——
   `晚 N 天 / 早 N 天 / 正好`；没有计划时就预测六级整本（「按这个速度，六级还要 152 天」）。
   **没有实际记录时整行不显示**，不编数字。

> ⚠️ **第五版改掉了第四版的「目标线」**：那是一条贯穿整行的发丝线 + 一个「目标」小标 ——
> 全 0 时线被顶到图形区最上面，横贯整行**看起来就是一条分割线**，小标还正好贴在上一行数字下面，
> 用户截图指出「这里 UI 还是乱的」。现在改成底柱，两个问题一起没了。
> 两根柱子都绝对定位贴底（`barSlot` 里的 `ghostBar` / `chartBar`）——**共用同一条底线**；
> 用负 margin 那套会让灰柱浮起来（试过）。

- 「今天该背多少」用的是和封面「今日」那行**同一个数**（有计划听计划、没计划用每日目标），
  所以整页只有一个标准，不存在「按哪个算达标」；
- 柱子和目标线**共用一把尺子**：纵轴上限 = `max(今天该背的量, 最好的一天)`，
  所以「恰好做到目标」的那天，柱子顶正好落在线上（这一点单独断言过）；
- ⚠️ **文案里的日期一律走 `storage.shortDate()`**：预测出的完成日期很容易跨年
  （10 月按每天 12 个要背到明年 3 月），只写 `03-12` 会被读成「今年 3 月」—— 那是过去。
  同年显示 `MM-DD`，跨年显示完整 `YYYY-MM-DD`。
- 两个预测函数别混：`forecastByPace()` 永远用**最近实际速度**（「照我现在这样哪天能完」），
  `getPlanStatus()` 在「按每天数量」模式下用**你定的量**（「按我的承诺哪天完」）。

**累计那块**（`getStudyStats()`）全部从 `daily` 历史现算，**不另存字段**：总词数、学习天数、
当前连续 / 最长连续、今日 / 本周 / 近 30 天。⚠️ 历史只留最近 62 天（`pruneDaily`），
所以「最长连续 / 总词数」是**最近 62 天内**的账。


**计划页**（`pages/plan`）同一轮也压过：从「信息卡 + 三列数字网格卡 + 操作区」压成**一张卡**
（标签行 / 日期行 / 一条进度条 / 两行文字），同样的信息用「还剩 104 个词 · 每天 11 个」一句话说完。
**生词本页**顺手删掉了解释性废话（「（单词不在这里显示）」「这次复习几个」这个重复标签、
「按标记 7~1 分档看词 · 每档可随机抽查」压成「按标记分档 · 可随机抽查」）。

**两个为功能区新增的数据能力**（都只存本地、不上云）：

1. **7 天节奏**：`wordlord_state_v3.daily`（`日期 -> 当天词数`）是**历史**，不随零点清空，
   只在超出 62 天时裁剪；`addTodayWord()` 里顺手记一笔（和 `todayWords` 同一时刻写）。
   主界面封面的「近 7 天」细柱和「连续 N 天」都读它。
2. **连续天数**：**不是另存的打卡字段**，而是从 `daily` 往前数算出来的
   （`getStreak()`）。规则：今天背了就从今天起数；**今天还没背则从昨天起数** ——
   所以每天零点一到连续天数不会归零。这样也永远不会出现「打卡数」和「实际记录」对不上。
   这段日期逻辑单独验证过 4 个场景（断开 / 今天未开始 / 空数据 / 7 天全勤）。

**计划功能**（`pages/plan`，主界面子页，用户 2026-10 要求加）：

**期限驱动**，不是「每天背 N 个」——后者和已有的每日目标重复了。你说「11 月 10 日之前背完六级」，
页面立刻告诉你「那接下来每天要背 13 个词」，之后每天回来看一眼「领先还是落后」。

只存**四个事实**，其余全部现算（`storage.getPlanStatus()`）：

| 字段 | 含义 |
| --- | --- |
| `bookId` | 背哪本书（内置六级 / 上传的某本） |
| `deadline` | 目标日期（`YYYY-MM-DD`，用系统 `<Picker mode="date">` 选） |
| `startedAt` | 建计划那天 |
| `baseDone` / `scopeTotal` | **建计划时当场快照**「已掌握多少 / 共多少词」——计划期的起点和分母 |

⚠️ **两个刻度千万别混**（第一版就混了，18 条断言里的 3 条直接抓出来）：

- `done` / `scopeTotal` 是**整本书的绝对进度**（「已掌握 320 / 424」）——只有分子也用全书口径，
  「背完」才是能到达的 100%；如果分子用「计划期增量」、分母用「全书总词数」，
  那么建计划前已经掌握的那部分永远补不上，**计划永远无法完成**。
- `plannedDone`（应完成的绝对位置）从 `baseDone` 起算：
  `应完成 = baseDone + (scopeTotal − baseDone) × 已过天数 / 总天数`。
  领先/落后 = 绝对进度 − 应完成，所以建计划当天差值正好是 0。
- `每天要背 = 剩余 ÷ (剩余天数 + 1)`（含今天）→ 截止日当天就是「今天全背完」。
- 计划页**不再写「起点 N」**（2026-10 第三轮去掉）：那是内部概念，用户看不懂；
  基线的影响已经体现在「领先 / 落后 N 个词」里。`baseDone` 仍然存在，只作为计算起点。

三个联动：

1. 计划算出的「每天 N 个词」可以**一键写进每日目标**（主界面「今日 / 目标」那条进度条用的就是它）；
2. 主界面有计划的卡片，点一下进这一页；没计划就是一行「定个计划」入口；
3. 建计划时**快照基线**：之后又背了多少才算计划进度，不会把建计划之前背的算进计划成绩。

### 两种模式（用户 2026-10：「计划可以自行选择每天背多少个」）

| 模式 | 你定什么 | 它算什么 | 计划里存什么 |
| --- | --- | --- | --- |
| **按日期** | 目标日期 | 每天要背几个 | `deadline`，`perDay = 0` |
| **按每天数量** | 每天背几个（输入框，任意数量） | 哪天能背完 | `perDay`，`deadline = ''` |

- **只存一个驱动量**，另一个永远现算 —— 所以不会出现「日期和每天的量互相矛盾」。
  `setPlan()` 里就直接归一化：传了 `perDay` 就把 `deadline` 清空，反之亦然；
  `getPlan()` 会把两个都没有的脏数据当「没有计划」。
- 老计划没有 `level`（当整本）也没有 `perDay`（当按日期），两个缺省都在 `getPlan()` 里兜住。
- 「今天够了吗」和「领先/落后」两种模式都有，但**应完成的算法不同**：
  - 按日期：把要补的量按目标日期线性铺开；
  - 按每天数量：`起点 + 每天的量 × 已经过了几天`（按你自己定的节奏算今天应该到哪儿）。- **「会晚 / 能提前」只在预测基于实际速度时才显示** —— 按日期模式如果没数据、
  拿计划自己的节奏去预测，数学上必然「正好赶上」，显示出来就是废话（代码里用 `etaByPlan` 挡掉）。
- 按每天数量模式**没有目标日期，所以永远不会「过期」**，封面那行也不能说「剩 N 天」
  （会变成「剩 0 天」）—— 改成「每天 15 个 · 预计 10-23 背完」。

### 第三轮（用户截图反馈「好丑」）：先修「不合理」，再修「不好看」

截图里最刺眼的不是样式，是 **「每天 59 个词」+ 红字「还差 47 个」** —— 30 天背 1824 词本来就不现实，
页面还每天给人一次挫败。所以这轮的主体是**可行性**：

| 改了什么 | 为什么 |
| --- | --- |
| **可行性提示 + 一键放宽** | 每天要背超过 `HEAVY_PER_DAY = 40` 就直说「每天 59 个偏大，容易坚持不下来」，并给一颗胶囊一键调到 `COMFORT_PER_DAY = 30` 个/天（按日期模式自动算好新日期，按每天数量模式改成 30）。表单里也有同一套提示 |

### 第二轮：从「报数」到「能行动 + 能预测」

| 加的 | 回答用户真正会问的问题 |
| --- | --- |
| **档位**（整本 / 高频 / 中频 / 低频，ActionSheet 选） | 「我只想背高频词」——计划从「一本书」细化到「一本书的一档」 |
| **两种模式**（按日期 / 按每天数量） | 「我不想被日期绑住，我想每天固定背 15 个」 |
| **今天 N / M 个词 · 已达成 / 还差 K 个** | 「我今天够了吗」 |

- **预测口径**（`avgPerDay`）：分母用最近 7 天里**有记录的天数**（中间空几天不该把速度拉低），
  所以页面把平均值也写出来（「每天约 13 个」），让用户自己判断这个速度现不现实。
  预测只在「有记录 + 还有剩余」时给，否则老实说「最近没记录，先背几个才能预测」。
- ⚠️ **符号约定**（写反了就是「明明来不及却告诉你来得及」，最危险）：
  `etaLateDays = daysBetween(deadline, etaDate)`，**正数 = 预计日期晚于目标 = 会晚到**，
  **负数 = 能提前**，0 = 正好赶上。页面分支和这条约定一起断言过。
- 计划页排版沿用封面那套：**一张卡 + 一条对齐的表**（标签列 144rpx：进度 / 今天 / 节奏 / 预计），
  进度只有一条 4rpx 细条，没有第二张卡、没有数字网格。
- 老计划没有 `level` 字段：`getPlan()` 会把它当成 `all`（整本）读出来，不会让已有计划失效。

边界都处理了：今天到期（`daysLeft = 0`、未过期）、已过期、整本（或某一档）背完（`finished`、每天 0）、
上传的词书被删（`bookMissing`，页面明说「这本词书已经不在了」而不是白屏或假数据）、
「撤回掌握导致掌握数低于基线」（`done` 不为负、显示落后）、「最近 7 天没有任何记录」（不预测）。
日期用 **UTC 零点解析**，跨月跨年不受时区和夏令时影响（`10-31 + 1 天 = 11-01`、
`12-31 + 1 天 = 次年 01-01` 都断言过）。
计划只存本地、不上云：它是这台手机上的节奏，换手机重定一个就行。

- **只有两种动作算数**（用户 2026-10 明确）：
  ① 点击七级标记（`incrementMark` 成功那次）、② 点「我会了」（`masterWord`）。

- 写入点就在 `storage` 的 `incrementMark()` / `masterWord()` 里，所以**在哪一页动手都算**

- **每天本地零点之后自动清零**：所有读写今日计数的入口都先过一遍 `resetToday()`
  （跨天就清空）；后台放一夜再回前台，`useDidShow` 里也会重读一次。
- 同一个词今天点几下都只算一个词；换词书 / 换档次算同一个数字（跨书累计）。
- 首页那行「今日：翻了 N 页 · 标记了 M 个词」用的是同一份今日计数（`loadTodayCounts()`），
  其中「标记了 M 个词」数的是**点击次数**（同一个词点三下算三下），和这个去重的词数不是一个口径。

- 最下面一行**灰色小字**「查看全部生词（N）›」—— 用户要求这个入口「小一点、不那么明显」，

**复习**（`pages/review`，生词本子页，从「开始复习 N 个」进）：**一屏一个词**，
先只给英文，点卡片才露释义。两个动作 + 一个出口：

| 动作 | 结果 |
| --- | --- |
| 我会了 | `masterWord()`：标记清零 + 标为掌握 → 词离开生词库、进「熟练掌握词汇」 |
| 还不认识 | 标记次数 +1（到 7 为止），词留在生词库，下次复习还会碰上 |
| 跳过 | 不判也不记，单纯往前走（复习记录里不会出现它） |

**这一批挑哪几个词**由 `storage.pickReviewBatch()` 定：**优先刚在翻书页标记过的词**
（按 `markedAt` 倒序，老数据没时间戳的排最后）。判过的词**当场**写进复习记录，
所以半路退出去也不白复习；整批走完是结算页（我会了 X / 还不认识 Y / 跳过 Z）。
这一批是**进页面时的快照**，复习过程中词离开生词库也不会让眼前的列表跟着缩水。

**复习记录**（`pages/review-log`，生词本子页）：**按标记段位分档的目录**，7 → 1 七行，
每行「标记 N 次 + 这一档有几个词 + 灰色箭头」（这一档没词时整行压暗、点了不动）。
顶部一行「生词库共 X 个词 · 复习过 Y 个」。点进某一档是 `pages/review-level`。

**标记档位**（`pages/review-level?level=1..7`，复习记录的下一层）——用户对这一页的定位是
「**主要功能是一下子看到当前标记段位的单词，很明了**，随机抽查只是辅助功能」，所以：

1. **顶部一张抽查卡**：「抽一个」→ 从这一档里随机抽一个词，先只给英文，点词看释义，
   还能「再抽一个」或者直接「我会了」。抽中概率按「最近标记 / 复习过」加权
   （`storage.pickRandomByRecency()`：一周以内线性加成，最多 **1.5 倍**——用户要的是
   「概率大一点点」，不是「只抽新词」）。
2. **下面是这一档的全部单词**：词 + 音标词性 + 释义全摊开，行尾小字写「复习 N 次 / 未复习」。
   排序按**最近标记的在前**。**只读列表**：标记、掌握这些动作回翻书页 / 全部生词 / 复习页做。

**复习记录（`reviews`）+ 标记时间（`markedAt`）这两份数据都不上云**：它们是这台手机上的
复习节奏，用来排序和加权，丢了不影响标记 / 掌握这些真数据。


起因：加了「主界面 → 词书列表」这一层之后，词书列表需要返回，而**自定义导航栏没有系统返回按钮**
（navigationStyle: custom 会把原生返回一起隐藏），原来 `big` 分支根本没有箭头，会走不回去。
带箭头的 big 栏更高，所以用 `bigNavBarHeightPx(true)` 算内边距 —— **这个布尔值必须和页面上的 `back` 一致**，
否则第一个条目会被压在标题底下。
主界面（`pages/home`）**不用导航栏**：它是封面，内容一屏铺满、不滚动，没有返回可给。

**上传**：CSV 列序固定 `word,phonetic,pos,definition`（有表头会自动跳过），存本地缓存，
每上传一次就在「我的上传」里新增一本词书（书名取文件名），导入后自动分好高 / 中 / 低频。

## 2026-10 UI 复核（对比度 / 热区 / 按下态）

这一轮是拿 `weapp-ui` 技能（本机 `~/.dsh/skills/weapp-ui/`，按小程序平台重写过的 UI 评审流程）
过了一遍五个镜头之后改的：**无障碍 → 平台惯例 → 工艺 → 打磨**。原则是**只改数值和反馈，
不动设计语言**（仿苹果 + 液态玻璃那套一个字没改）。

### 1. 对比度：全部按真值算，不靠感觉

小字（≤24rpx）要 ≥4.5:1，大字（≥32rpx 或粗体）≥3:1。改之前有四处不达标：

| 位置 | 改前 | 对比度 | 改后 | 对比度 |
| --- | --- | --- | --- | --- |
| 全站次要文字（音标/说明/页码/Tab 标签） | `#86868B` | **3.62:1** ❌ | `#6E6E73` | **5.07:1** ✅ |
| 「已掌握」药丸的字 | `#34C759` | **1.97:1** ❌❌ | `#1E7A34` | **4.80:1** ✅ |
| 红色文字链接（移除/撤回/删除） | `#FF3B30` | **3.6:1** ❌ | `#D70015` | **5.38:1** ✅ |
| 空标记圆圈描边（非文字控件要 ≥3:1） | `#D2D2D7` | **1.66:1** ❌ | `#8A8A90` | **3.43:1** ✅ |

- `#FF3B30`、`#34C759`、`#E8F5E9` **仍然是填充/状态色**（圆圈、绿底），只是不再当小字色用。
- 已掌握的词在翻书页压暗用 `COLOR.wordDone`（`#8E8E93`，3.26:1）—— 它是 40rpx 大字，3:1 就够。
- 灰色箭头 `#C7C7CC` 保持很浅：整行都可点，箭头是**装饰**，不算控件。
- 首页那行「今日：**背了 N 个词** · 标记 M 次 · 翻 N 页」和翻书页的「今日已背」是同一个口径
  （`todayWords`，去重），后面两项写清了量词（次 / 页）—— 同一个词在两个页面上必须同一个意思。

### 2. 热区：从 44rpx（22pt）提到 88rpx（44pt）

44rpx 是全站最矮的可点区域，太低了。做法统一是「**外套一层 88rpx 的盒子，再用负外边距把多出来的部分还给布局**」，
所以**卡片和行高基本没变**：

| 元素 | 改前 | 改后（热区） | 视觉 |
| --- | --- | --- | --- |
| 标记圆圈 | 44rpx | **88rpx** | 44 → **56rpx**（28pt，两位数标记不再挤） |
| 「我会了」药丸 | 高 44rpx | **高 88rpx** | 不变（44rpx） |
| 底部 Tab 标签 | 高 36rpx | **高 88rpx** | 栏高 52 → **104rpx**（≈微信原生 TabBar 的节奏） |
| 列表行的文字区 / 箭头 / 删除 | 70 / 68 / 48rpx | **88rpx** | 不变 |
| 底部胶囊（上一页/下一页） | 88rpx | 已达标 | 不变 |

⚠️ `tabBarHeightPx()`（metrics.ts）跟着从 52rpx 改成 **104rpx**，所有页面的底部内边距都引用它，自动跟随。

### 3. 按下态：全站补上 `hover-class`

原来点任何东西都**毫无反馈**（微信里 `:hover` 和 `cursor` 完全无效），这是「塑料感」的主要来源。
现在 `theme.ts` 导出 `PRESS = { hoverClass: 'press', hoverStartTime: 0, hoverStayTime: 80 }`，
可点元素一律 `<View {...PRESS} onClick={...}>`，`.press { opacity: 0.55 }` 在 `app.css`。
`hoverStartTime: 0` 是必须的 —— 默认 50ms 才亮，快点根本看不到。

### 4. 长列表：分批展开

ScrollView **不虚拟化**，「一次看全部」的页面（全部生词 / 标记档位）原来会一次性铺出所有卡片。
现在按 **80 个一批**渲染，底部一颗「显示更多（还剩 N 个）」再放一批 —— 诉求保留，开屏不再挂上千节点。

### 5. 字色/危险色语义

`COLOR.danger`（`#FF3B30`）＝填充与状态，`COLOR.dangerText`（`#D70015`）＝**文字**。
新加文字时别再用 `danger` 当 24rpx 的链接色。

### 6. 这轮**没有**动的东西（故意的）

- 仿苹果那套版式、留白节奏、玻璃配方、圆角层级、深色（仍明确不做）都没改；
- 深色模式**依然不做**：整套做要动 `theme.json` + 每个页面的硬编码色，属于独立一轮；
- 长按撤回**仍然只有长按**，但它的等价可见入口在「熟练掌握词汇」页（顶部静态提示 + 行尾「撤回」链接），
  所以「隐藏操作没有提示」这条是**满足**的，不是在翻书页再堆一行说明。

## 液态玻璃（Liquid Glass）

用户 2026-09-28 要求的整体风格：像 iOS 26 控制中心那样通透、轻盈。
**这一轮推翻了当天早些时候的「纯白底、不要渐变、不要阴影、不要圆角卡片」**，别再按那几句往回改。

- **页面底色**：`#F5F5F7` → `#FFFFFF` 渐变（`STYLE.container`），兜底还写着纯白底色
- **玻璃配方**：全在 `src/app.css`，四个 class ——
  `.glass`（半透明白 0.7 + `backdrop-filter: blur(20rpx) saturate(180%)`）、
  `.glass-bar-top` / `.glass-bar-bottom`（导航栏、Tab 栏，加一道极细的白色高光边）、
  `.glass-card`（列表行，圆角 24rpx + 1rpx 白边 + 极淡投影 `0 4rpx 24rpx rgba(0,0,0,0.05)`）、
  `.glass-pill`（胶囊按钮）
- **为什么写在 CSS 里而不是行内 style**：行内样式走 Taro 的样式白名单，写不了 `-webkit-*`；
  写在 CSS 文件里更自由。代价见下面两条坑
- ⚠️ **坑一：那个文件里的 `px` 会被 Taro 按 1:1 换成 `rpx`**（designWidth 750 的约定）。
  **想要 20rpx 就得写 20px** —— 我第一版写 `blur(10px)`，产物里是 `blur(10rpx)`，只有一半。
  不想被换算的可以写大写 `PX`（Taro 跳过）
- ⚠️ **坑二：`-webkit-backdrop-filter` 会被 WXSS 编译器整个丢掉**（实测产物里只剩标准属性），
  所以 **iOS 18 之前的老系统 / 部分 Android 上玻璃退化成「半透明白」，不糊**。
  底色本来就是半透明白，退化后可读性不受影响，可接受
- **玻璃要「真穿透」才有意义**：导航栏、`上一页/下一页`、Tab 栏都改成**浮在滚动内容上面**
  （`STYLE.topBar` / `STYLE.bottomBar`，absolute + zIndex 10），单词从它们底下滚过去才有东西可糊。
  代价是**每个页面都要给滚动内容留出上下内边距**，高度都算在 `src/utils/metrics.ts`
  （`navBarHeightPx` / `bigNavBarHeightPx` / `tabBarHeightPx` / `rpxToPx`）。
  改导航栏或 Tab 栏的高度，记得同步那个文件
- **主按钮（「下一页」「上传 CSV 词表」）保持黑色实心**（用户选的）：玻璃 + 一个 tinted 主按钮
  才是 iOS 26 的做法，全玻璃会让主操作失去强调
- **状态色不玻璃化**：标记圆圈的 7 级填充色、已掌握的浅绿底 `#E8F5E9` 都是语义色，
  换了就跟旁边的玻璃糊在一起
- **翻书页的条目故意没做成卡片**：那页要的是「备忘录打开一篇笔记」的大片留白，卡片会把留白切碎。
  玻璃只出现在翻书页的悬浮件上（导航栏、上一页胶囊、我会了药丸、Tab 栏）
- 列表行变成卡片后，卡片内边距上下各 32rpx + 行间 16rpx 的缝 = 文字行之间仍然 80rpx，
  和上一版「上下各 40rpx 靠留白分行」的节奏一致

## 屏幕安全区

用户 2026-09-28 的要求：左右至少 32rpx、离屏幕底至少 48rpx（并避开底部横条）、
顶部内容距导航栏至少 24rpx、任何元素都不许被屏幕边缘裁掉。全部落在 `src/utils/metrics.ts`。

- **左右 32rpx**：一律用 `PAGE_PAD`。卡片是「外边距 32rpx + 内边距 32rpx」，
  所以卡片里的文字实际离屏幕边 64rpx；翻书页条目是 padding 32rpx（正好贴线）；
  导航栏返回箭头的**墨迹**离左边约 36rpx（按钮盒虽然从 0 开始，但字形是居中的）
- **离屏幕底 48rpx**：用 `bottomSafePx()` = **max(48rpx, Home 指示条高度)**。
  两个数都要：只写 48rpx 的话，全面屏的横条区域是 34px（≈68rpx），按钮会压在横条上；
  只写 inset 的话，非全面屏（iPhone SE 那类）inset 是 0，标签会贴着屏幕底边。
  用在：Tab 栏底部的 spacer、上传页底部按钮条的内边距。
  翻书页的胶囊浮在 Tab 栏上面（`bottom` = Tab 栏高度），所以离屏幕底远大于 48rpx
- **顶部 24rpx**：`topGapPx()`，各页滚动内容的 `paddingTop = 导航栏高度 + 24rpx`
  （卡片自己还有 16rpx 外边距，所以第一张卡片实际离导航栏 40rpx）。
  **翻书页没加**——它的条目自带 36rpx 上内边距，本来就 > 24rpx，加了反而白吃屏幕高度
- **导航栏标题不许钻到微信胶囊底下**：胶囊是系统画在最上层的，宽度/位置各家机型、
  各家微信版本都不同，所以问 `getMenuButtonBoundingClientRect()` 现算
  （`navTitlePadPx()`，左右取同一个值保证标题居中），**不能写死**
- **取尺寸用的是 `Taro.getWindowInfo()`**（= `wx.getWindowInfo()`），不是
  `wx.getSystemInfoSync()`：字段完全一样（windowWidth / statusBarHeight / safeArea），
  但后者从 2021 年起就被官方标为废弃（基础库 2.20.1 起推荐按需取），所以用新的
- **长字符串不许顶出屏幕**：`app.css` 的 `.text-break`（`overflow-wrap: anywhere`）。
  用户传的词书**书名就是文件名**、昵称也是随手填的，都可能是没空格的长串；
  微信里 overflow 默认 visible，长串会冲出卡片、冲出屏幕右边。
  用 `anywhere` 而不是 `word-break: break-all`：后者会把正常英文单词从中间劈开，
  前者只在「这串放不下这一行」时才断，而且参与 min-content 计算，
  能治 flex 子项的经典溢出。注意 Taro 白名单里**没有** wordBreak / overflowWrap，只能走 CSS 文件
- 导航栏标题超长走 `WebkitLineClamp: 1` 出省略号，不裁切、不换行

## 登录与云同步

标记、已掌握、上传的词书、翻到第几页都会同步到微信云开发，
换台手机用同一个微信登录就能全部拿回来。

**没开通云开发也能正常用**：`src/cloud/config.ts` 里的环境 ID 是空的时候整条云链路静默关闭，
数据只存本地，「我的」页显示「云同步未开通」。所以下面这 5 步随时可以做，不做也不影响背单词。

### 开通步骤（5 步，全部免费，基础版就够）

1. **确认 AppID 是真实的小程序 AppID**。云开发不支持测试号 ——
   `project.config.json` 里的 `appid` 现在是 `wxf46a75f64921bdca`，这个是你自己注册的，没问题。
2. **开通云开发**：微信开发者工具打开本项目 → 顶部工具栏点「云开发」→ 按提示开通 →
   新建环境时**套餐选「基础版」**（免费的）→ 环境名随便填（比如 `wordlord`）。
   > ⚠️ 新开通的环境要**等大约 10 分钟**才能用，太早调用会报 `invalid scope`，不是配置错了。
3. **建三个集合**：云开发控制台 →「数据库」→ 右上角「+」新建集合，名字分别叫
   `user_words`、`user_books`、`user_profile`。**权限保持默认（仅创建者可读写）不用改** ——
   所有读写都走云函数，云函数是管理员身份，不受权限设置限制。
   | 集合 | 存什么 |
   | --- | --- |
   | `user_words` | 一个词一条记录：`word` / `markCount`(1–7) / `mastered` |
   | `user_books` | 一本上传的词书一条记录（含全部词条） |
   | `user_profile` | 头像、昵称、阅读位置（最后翻的书/档 + 每档第几页） |
4. **上传云函数**：在开发者工具左侧文件树里找到 `cloudfunctions/wordlord`，
   **右键 →「上传并部署：云端安装依赖」**。等它跑完（第一次要装依赖，一两分钟）。
5. **填环境 ID**：把第 2 步拿到的环境 ID（形如 `wordlord-3gxxxxxxxxxxxx`，
   在云开发控制台左上角环境名旁边，或「设置 → 环境设置」里）填进
   `src/cloud/config.ts` 的 `CLOUD_ENV_ID`，然后重新构建：

   ```bash
   npm run build:weapp
   ```

   回开发者工具重新编译 → 进「我的」页，应该显示「微信登录 · 数据已同步到云端」。

**怎么验证真的同步了**：翻书标几个词 → 看「我的」页状态是不是「微信登录 · 数据已同步到云端」
→ 去云开发控制台的 `user_words` 集合里应该能看到那几条记录（`_openid` 是你的）。
换手机测试：用同一个微信在另一台手机打开（或用开发者工具「清除全部缓存」模拟新设备），
数据应该自动回来。

### 关于「一键登录」的真相（和常见 App 不一样，值得看一眼）

- **登录是静默的，没有授权弹窗**。openid 由云函数里的 `getWXContext()` 直接给出，
  不需要用户点任何东西 —— App 一启动就已经登录好了。
  （你要求里说的「`wx.login()` 拿 code 换 openid」是**以前的写法**：那条路要自己维护
  session、还要处理 code 过期。用云开发之后 openid 是白送的，不需要 code，
  少一个会过期的中间态，所以没写 `wx.login()`。）
- **头像和昵称自动拿不到了**。微信 2022-10 起禁止小程序获取用户头像昵称
  （`getUserProfile` 现在只会返回「微信用户」+ 一个灰色默认头像）。现在唯一的合法路径是
  用户主动设置：**头像**用 `<Button open-type="chooseAvatar">` 让用户点一下自己选，
  **昵称**用 `<Input type="nickname">` 让用户自己填（微信键盘会给「使用微信昵称」的快捷填写）。
  所以「我的」页上这两项是**用户主动设置**的，没设置时显示「未设置昵称」+ 空头像圈。
- 因此「微信一键登录」按钮平时**不会出现**，只在云环境没配好 / 登录失败的时候出现，用来手动重试。
- 头像会传到云存储（`avatars/` 目录），存的是 fileID，所以换手机也能显示。

### 同步的时机和合并规则

- **推送**：本地每次改动（标记 / 长按撤回 / 我会了 / 撤回掌握 / 生词本移除 / 上传或删除词书 /
  翻页）都先标脏，**安静 1200ms 后合并成一次请求**推上云端 —— 连着标十个词也只发一次。
  推送失败会把脏数据留着，下次改动或下次启动时重试。
- **拉取**：只在登录时拉一次全量（App 启动时静默登录会触发）。
- **合并规则**（两边都可能有数据，必须能收敛，不能来回打架）：
  | 字段 | 规则 |
  | --- | --- |
  | `markCount` | 取两边**较大**的（次数是「标了多少下」，取大不丢信息） |
  | `mastered` | 取**或**（任何一台设备点过「我会了」就算掌握） |
  | `pages`（翻到第几页） | 取两边**较远**的那页 |
  | 上传的词书 | 按 id 合并，两边各有的都保留（id 是本机生成的，不会重名） |

  合并完如果本地跟云端不一致，会把新值回推一次，两边就对齐了。

### 为什么云端读写全走云函数，小程序端不直连数据库

1. **小程序端 `collection.get()` 一次最多返回 20 条**，拉全量标记得翻几十次页；
   云函数端一次 100 条，循环几轮就拉完了。
2. 云函数以**管理员身份**读写，不受集合权限设置影响 —— 控制台里把集合建出来就行，不用逐个调权限。
3. openid 由 `getWXContext()` 直接给出，不用自己算 `_openid`。
4. 云函数里出错是**正常返回** `{ ok: false, error }` 而不是 reject，客户端能准确知道
   「这次没传上去」，从而保留脏数据重试而不是当成成功把数据清掉。

云函数只有一个：`cloudfunctions/wordlord`，四个 action —— `login` / `pull` / `push` / `saveProfile`。

## 词库数据

`src/data/cet6.json` 是**六级大纲新增词（1824 词）**，按词频从高到低排列，
每个词条带音标 / 词性 / 中文释义：

```json
{ "word": "environmental", "phonetic": "/inˌvaiərənˈmentəl/", "pos": "adj.", "definition": "周围的；环境的" }
```

「新增词」= 六级大纲里**剔掉 cet4 / 高考 / 中考 标签**的词，也就是过了四级之后新要背的那些。
不收基础词，否则高频档里会排满 what / can / way 这类早就会的词，翻半天没有收获。

生成流程（`scripts/build-wordlist.mjs`）：

1. 取 ECDICT 里 `tag` 含 `cet6` 的词 + KyleBing 补充的词，合成六级大纲
2. 按 COCA 词频排序后截到 5500（六级大纲的规模）
3. 剔掉带 `cet4` / `gk` / `zk` 标签的 3669 个基础词、33 个专有名词 → 剩 **1824 词**
4. 对剩下的词算分档阈值，写出 `cet6.json` 和 `frequency.json`

## 词频分档

高频 / 中频 / 低频的**分档阈值是算出来的，不是写死的比例**，
对词表的 COCA 词频排名做 1D k-means(k=3) 聚类（在 `log10(排名)` 上做，
词频是重尾分布必须先取对数）：

| | 值 |
| --- | --- |
| 簇心（COCA 排名） | 3362 / 6231 / 10313 |
| 阈值 | 相邻簇心中点 → 取整 **4577 / 8016** |
| 稳定性 | 固定随机种子 + k-means++ 初始化 + 25 次重启取 SSE 最小，重跑结果逐字节一致 |

聚类在**构建期**完成（`scripts/build-wordlist.mjs` 里的 `kmeans1d`），
结果落成 `src/data/frequency.json`：`high`（4396 词）/ `mid`（3541 词）两段词表 + 两条阈值。
**内置词表和用户上传的词表在运行时走的是同一把尺子**（`bandOf()`），所以口径一致。

对内置词表（1824 词）的实际分档结果：

| 档次 | 词数 |
| --- | --- |
| 高频词 | 323 |
| 中频词 | 759 |
| 低频词 | 742 |
| 完整词表 | 1824 |

要重新生成词表和词频表：

```bash
node scripts/build-wordlist.mjs   # 原始数据已在 .worddata/ 里
```

数据来源：

| 来源 | 用途 |
| --- | --- |
| [skywind3000/ECDICT](https://github.com/skywind3000/ECDICT)（MIT） | `tag` 含 `cet6` 的词条，提供音标 / 词性 / 中文释义；`frq`(COCA) / `bnc` 词频排名用来排序和分档；`tag` 里的 `cet4`/`gk`/`zk` 用来识别基础词 |
| [KyleBing/english-vocabulary](https://github.com/KyleBing/english-vocabulary) | 补上 ECDICT 漏标的六级词 |

`scripts/build-wordlist.mjs` 会依次写出 `src/data/cet6.json` 和 `src/data/frequency.json`。

原始数据（`.worddata/`，约 65MB）已加进 `.gitignore`，要重新下载：

**`store/events.ts` 为什么存在**：`storage.ts` 是纯本地存储层，改完数据要通知同步层，
但同步层 `services/sync.ts` 反过来要 import `storage.ts` 才能读数据 —— 直接互相引用就成环了。
所以放一个谁都不依赖的空壳：`storage.ts` 改完往 `emitChange` 喊一嗓子，
`sync.ts` 在启动时用 `onChange` 接住。加新的「要同步的数据」时照着这个模式走。

| `wordlord_auth_v1` | 登录态：openid + 头像 + 昵称 + 上次同步时间 | ✅ `user_profile` |

都以**单词本身**为 key，所以同一个词在「高频词」和「完整词表」里共享标记进度；
翻页位置按 `词书id:档次` 分开记，换档次不会串页。

**今日计数故意不同步**：它记的是「今天这台手机翻了多久」，换台手机从 0 开始才是对的。
**每天词数历史、每日目标、标记时间、复习记录、「每次复习几个」也不同步**：它们是这台手机上的
节奏 / 排序 / 加权依据，和标记 / 掌握这种真数据分开（丢了只是顺序和柱状图回到默认，不影响学了什么）。
